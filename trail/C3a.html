tick_backward at the pop tick (clock = pop word, pop word neither -1 nor 0, 1 <= N <= 640): adds the mismatch count to healErr (as a 32-bit word), clears the pop state, undoes the swirl tick, returns 1
The reviewed wording of this result (its class sentence, C3a.txt) 
Rewinding through the puncture is proved on the exact bytes of vortex_a1.wasm (sha256 a3cf8c82), in Hearth's model of WebAssembly, integer code only, for the module's 4 MiB memory layout with the model's vortex count (model word 1) N between 1 and 640: whenever tick_backward runs with the clock word equal to the pop word (pop word neither -1 nor 0), the module adds to header word 5 (healErr), as a 32-bit word, the live-droplet count plus the number of rim, ripple and wobble checks that disagree with the values the puncture seeds from the speed table; it then clears pop header words 6..29, the whole speed table, the rim, ripple and wobble rings and every droplet word, sets the droplet count to 0 and the pop word to -1, and undoes the swirl tick exactly as the proved no-pop backward tick does, returning 1. Memory writes stay inside the clock/pop header words [16392,16512), the speed table, the vortex, ring and droplet arrays and the scratch area [1966080,2039808); the scratch area and the unused vortex words are not pinned. On the state the puncture is designed to leave, that count is 0 for every speed table (a proved statement about that state); that the puncture code actually leaves that state is tested on 300 real punctures and is not proved here (rung C3b). The count equals the true number of mismatches when at most 16384 droplets are recorded (the module's capacity); otherwise it can wrap. The forward puncture is not covered, and the host not writing memory or globals between calls is an assumption, not a WebAssembly guarantee.
