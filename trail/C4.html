In Hearth's model of WebAssembly, on the exact bytes of vortex_a1.wasm (sha256 a3cf8c82), start from tick 0 with no puncture (pop word -1), a model of N vortices with 1 <= N <= 640, and a clean memory (va1_clean: header words 6..31, the speed table, the pop arrays RA, RB, JQ, JP, ZQ, ZP, the droplet words and the droplet count all zero; init is TESTED, not proved, to leave this state). Click form: if the auto-pop word is 0 or above K, with K >= 1, K + 520 < 2^32 and n <= 520, then K calls of the shipped tick_forward each return 1; then, for EVERY memory that a successful click puncture may leave according to a TESTED relation (not proved: the puncture builds its speed table in floating point; the relation says it sets the pop word to the clock, sets RA to 251658, RB from that table, ZP from the model and the other pop data to zero, and changes nothing outside the table, the pop arrays, header words 6..29, the pop word, the droplet count and a 96-byte stack area), n tick_forward and then n + K tick_backward calls each return 1 and leave the module as it started: the same tick, pop and auto-pop words, model and vortex words in use, still clean, healErr unchanged, and every byte of its 4 MiB memory equal to the start except the scratch area [1966080,2039808), the unused vortex slots VA/VB[3N..2048) and the puncture's stack area [16288,16384). Both forms also hold when the film runs to the end of the pop: 520 forward calls, one more forward call that returns 0 and changes nothing, then 520 + K backward calls. Assumed, as in WebAssembly and not proved: between calls the host writes neither memory nor globals, and memory does not grow.
